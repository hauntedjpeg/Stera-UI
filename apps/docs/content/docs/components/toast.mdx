## Design

<DesignGuidelines>

### When to use

- Feedback on an action the user just took, where the outcome is worth confirming but not worth interrupting for: "Changes saved", "Event created", "Export failed".
- An outcome that arrives while the user's attention is elsewhere, such as a background job finishing.
- A result the user may want to act on straight away, with one follow-up such as Undo or Retry.

### When not to use

- Anything the user must acknowledge before continuing, or whose consequence is serious enough to stop them. Use an [Alert Dialog](/components/alert-dialog).
- A condition that stays true until something changes, such as an unverified email or an expiring plan. A toast leaves and takes the message with it. Use a [Callout](/components/callout).
- Validation messages tied to a particular input. Use the error treatment on [Field](/components/field).

### Guidelines

- Keep it to a short title and at most one line of supporting detail. A message that needs more than that needs somewhere the user can read at their own pace.
- Match the type to the outcome: `success` for a completed action, `error` for one that failed, `warning` for something worth knowing before continuing, `info` for neutral detail, and `loading` for work still running. Put the meaning in the copy as well, so it never rests on the icon or its color alone.
- Resolve a `loading` toast into `success` or `error` rather than adding a second toast. One outcome, one message.
- Give a toast at most one action, and only one the user would plausibly take right then: Undo, Retry, View. Anything they can return to later belongs elsewhere.
- Never make a toast the only record of something that matters. It goes away on its own, and anyone looking elsewhere misses it.
- Your call: where toasts are anchored, and how many stack before the oldest retires. Pick a position clear of primary content and navigation, and use it everywhere so people learn where to look.

See also: [Theming](/design/theming).

</DesignGuidelines>

## Usage

Add `<Toast />` once at the root of your app (e.g. in your layout), then trigger toasts with `toastManager.add(...)` from anywhere in your code. `toastManager` is a singleton, so it works in event handlers, server actions, or any module — no hook required.

```tsx
import { Toast } from "@/components/ui/toast"

export default function Layout({ children }) {
  return (
    <>
      {children}
      <Toast />
    </>
  )
}
```

```tsx
import { toastManager } from "@/components/ui/toast"

toastManager.add({
  type: "success",
  title: "Event has been created",
  description: "Sunday, December 03, 2023 at 9:00 AM",
})
```

Inside a React component, you can also use `useToastManager()` to access the same API along with the live list of toasts.

If you need an isolated manager — for example, multiple `<Toast />` viewports, scoped state in tests, or keeping a feature's toasts separate from the app-wide queue — create one with [`createToastManager()`](#createtoastmanager) and pass it via the `toastManager` prop.

## Toast Types

<ComponentPreview name="toast-types" caption="Toast Types" />

Pass a `type` to switch the leading icon and color treatment. Built-in types: `success`, `info`, `warning`, `error`, `loading`. Omit `type` for a plain toast with no icon.

| Type | Description |
| --- | --- |
| _(none)_ | Default notification |
| `success` | Success confirmation |
| `info` | Informational message |
| `warning` | Caution or advisory |
| `error` | Error or failure |
| `loading` | In-progress operation |

## API Reference

Built on Base UI's [Toast](https://base-ui.com/react/components/toast#api-reference) primitive — see the full API reference there.

### `<Toast />`

Drop-in viewport that renders the provider, portal, viewport, and a default toast layout. Use it once at the root of your app.

| Prop | Type | Default |
| --- | --- | --- |
| `position` | `"top-left" \| "top-center" \| "top-right" \| "bottom-left" \| "bottom-center" \| "bottom-right"` | `"bottom-right"` |
| `limit` | `number` | `3` |
| `timeout` | `number` (ms, `0` to disable auto-dismiss) | `5000` |
| `toastManager` | `ReturnType<typeof createToastManager>` | `toastManager` |

Pass a `toastManager` to swap the default singleton for a scoped manager created with `createToastManager()`.

### `createToastManager()`

Returns a fresh toast manager. Use it when you need an isolated queue — multiple viewports, tests, or feature-scoped notifications. The default export `toastManager` is simply `createToastManager()` called once at module load.

```tsx
import { createToastManager, Toast } from "@/components/ui/toast"

const billingToasts = createToastManager()

export function BillingArea() {
  return (
    <>
      <Toast toastManager={billingToasts} />
      {/* billingToasts.add(...) only renders here */}
    </>
  )
}
```

### `toastManager`

A singleton created with `Toast.createToastManager()` from Base UI. Use it to trigger toasts from anywhere.

| Method | Description |
| --- | --- |
| `add(options)` | Create a toast. Returns the toast id. Reusing an existing id updates the toast in place. |
| `update(id, options)` | Update an existing toast. |
| `close(id?)` | Close a specific toast, or all toasts when called with no id. |
| `promise(promise, { loading, success, error })` | Render an async toast that transitions through `loading` → `success` / `error`. |

`add` accepts: `id`, `type`, `title`, `description`, `timeout`, `priority`, `actionProps`, `onClose`, `onRemove`, and `data`. See the [Base UI Toast docs](https://base-ui.com/react/components/toast) for the full option list.

### Lower-level parts

For custom layouts, compose the parts directly: `ToastProvider`, `ToastPortal`, `ToastViewport`, `ToastRoot`, `ToastContent`, `ToastTitle`, `ToastDescription`, `ToastAction`, `ToastClose`. Each is a thin wrapper around the matching `Toast.*` part from `@base-ui/react/toast`. `useToastManager` is re-exported from Base UI's `Toast.useToastManager`.
